# Requirements Traceability Matrix (RTM)

> Last updated: [YYYY-MM-DD]
> Generated by: `/architecture-review rtm`
> Registry version this snapshot was built from: [version field of tr-registry.yaml]

**What this is.** One row per technical requirement, carried all the way from the
GDD that stated it to the test that proves it works: **GDD → ADR → Story → Test**.
It is the document you hand a release gate when the question is "which
requirements have nothing testing them?".

**Written by** `/architecture-review rtm` — Phase 3 builds the coverage columns,
Phase 3b globs `production/epics/**/*.md` for the story that carries each TR id and
`tests/` + `tools/*_check.gd` for the evidence file that story names.
**Read by** the release gate, `/qa-plan` when scoping a sprint's test work, and
`/regression-suite` when hunting requirements with no coverage.

**How to fill it:** run `/architecture-review rtm`. It regenerates this whole file.
There is nothing to hand-write here.

---

## THE ONE RULE: this file is DERIVED — `tr-registry.yaml` is the source of truth

`docs/architecture/tr-registry.yaml` is the only place a TR id is minted, and the
only place `requirement`, `adrs` and `status` are authoritative. This document is a
**regenerated snapshot** of that registry with two columns the registry has no
fields for — the implementing **Story** and its **Test** evidence.

- Never mint a TR id here. Never edit an id, a requirement text or a coverage
  status here — edit the registry and re-run.
- If this file and the registry disagree, **the registry wins** and this snapshot
  is stale. Re-run `/architecture-review rtm`.
- Two homes for one artifact is how a stack drifts. This has one home; that home is
  the registry.
